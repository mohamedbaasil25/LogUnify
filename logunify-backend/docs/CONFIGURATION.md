# Configuring secrets (environment variables, never code)

The audit of the repository found **no real credentials in code, config files or docs**. What it did find were dummy values
in test fixtures (`hunter2`, `legacy-key`, `test-hec-token`, a fake `AKIA...` key used to test redaction) and one all-zero Splunk HEC token
placeholder, now replaced by `${SPLUNK_HEC_TOKEN}`. Every real secret is read from the environment or a secret file, at runtime.

## Backend (`LOGUNIFY_*`, pydantic `SecretStr`: never printed, never returned by the API)
Set them as real environment variables (systemd `EnvironmentFile`, Docker/Kubernetes secrets, CI secret store) or in an untracked
`logunify-backend/.env` copied from `.env.example`. `.env` is git-ignored; `.env.example` holds only `change-me` placeholders.

| variable | purpose | generate with |
|---|---|---|
| `LOGUNIFY_JWT_SECRET` | signs/verifies bearer tokens when `LOGUNIFY_AUTH_MODE=jwt` (>= 32 bytes) | `python -c "import secrets; print(secrets.token_urlsafe(48))"` |
| `LOGUNIFY_AUDIT_HMAC_KEY` | keys the audit-log hash chain | same |
| `LOGUNIFY_ALERT_API_KEY` | legacy `X-API-Key` for `/api/v1/alerts*` | same |
| `LOGUNIFY_ALERT_WEBHOOK_SECRET` | HMAC-signs alert webhooks | same |
| `LOGUNIFY_ALERT_SMTP_PASSWORD` | SMTP login | from your mail provider |
| `LOGUNIFY_PII_HASH_KEY` | keyed pseudonyms when `LOGUNIFY_PII_MODE=hash` | same |
| `LOGUNIFY_MISP_KEY` | MISP automation key | MISP UI |
| `LOGUNIFY_ES_FORWARD_API_KEY`, `LOGUNIFY_ES_API_KEY` | Elasticsearch API keys (write-only vs. read-only monitoring) | Kibana / `POST /_security/api_key` |
| `LOGUNIFY_ALERT_WEBHOOK_URL` | webhook URL (often itself a secret): only `scheme://host` is ever logged | your chat/SOAR tool |

```bash
# one-off, current shell only (Git Bash / Linux / macOS)
export LOGUNIFY_JWT_SECRET="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
export LOGUNIFY_AUTH_MODE=jwt
python -m uvicorn app.main:app
```
```powershell
# Windows PowerShell (current session)
$env:LOGUNIFY_JWT_SECRET = python -c "import secrets; print(secrets.token_urlsafe(48))"
$env:LOGUNIFY_AUTH_MODE = "jwt"
```
Secrets in command lines end up in shell history and process listings: prefer an env file with `chmod 600`, or your platform's secret store.
Source HTTP tokens are generated by the API, shown once, and only their SHA-256 is stored.

## Vector forwarder
Secrets are files in `SECRETS_DIR` (default `/run/secrets`), referenced as `SECRET[fwd.<name>]`: `es_authorization` (contains
`ApiKey <base64>`), `splunk_hec_token`. Mount them from Docker/Kubernetes secrets. Endpoints (`ES_URL`, `SPLUNK_HEC_URL`, ...) are plain
environment variables (see `logunify-forwarder/README.md`).

## Splunk HEC token
`splunk/inputs.conf` contains `token = ${SPLUNK_HEC_TOKEN}`. Splunk does not expand variables, so render it at deploy time:
```bash
export SPLUNK_HEC_TOKEN="$(uuidgen)"     # store in your secret manager; the same value goes into SECRETS_DIR/splunk_hec_token
envsubst '${SPLUNK_HEC_TOKEN}' < splunk/inputs.conf > "$SPLUNK_HOME/etc/apps/logunify/local/inputs.conf"
```
(The quoted variable list keeps `envsubst` from also expanding `$SPLUNK_HOME` in the file.)

## Elasticsearch setup script
`python elasticsearch/setup.py --url https://es.internal:9200` reads the Authorization header from `ES_AUTH_HEADER`
(`export ES_AUTH_HEADER="ApiKey <base64>"`) so it stays out of shell history; the `--auth` flag exists but avoid it.

## Dashboard
`LOGUNIFY_API_URL` is the only variable (server-side proxy target, not secret). A user's JWT is pasted into the "Access token" button and
kept in `sessionStorage` for that tab only; never bake a token into `NEXT_PUBLIC_*` variables (those are shipped to every browser).

## Rotating and checking
* Rotate anything that was ever committed or pasted into a chat/ticket; changing `LOGUNIFY_JWT_SECRET` invalidates all issued tokens.
* Before committing: `git grep -nEi "secret|token|api[_-]?key|hooks\.slack" -- ':!*/tests/*'` and expect only code that handles secrets,
  `change-me` placeholders and `SECRET[...]` references. A secret scanner (gitleaks, trufflehog) in CI is a better long-term guard.
